# The harness: how Weaver implements the continuity contract

This doc explains the shape of the MVP — what is durable, what is disposable, and where each kernel invariant lives in code. Read [README.md](../README.md) first for the thesis.

## The split

The **durable layer** is a single typed document per workstream (`state/<slug>/workstream.json`, schema in [`src/types.ts`](../src/types.ts)) plus content-addressed artifacts (`state/<slug>/artifacts/`). It holds direction (decisions with supersession lineage), work (assignments with attempt history and adoption state), deliverables (with pinned content hashes), interactions (draft → approval → send → receipt → reply as separate facts), results (evaluated observations and replies), waits (wakes as stored data), human steering, the needs-you queue, and provenance (pass records, a bounded event tail). Every organizational write bumps a revision. Append-only printout sidecars retain exact before/after operator history without becoming coordinator input or changing that revision.

The durable layer has three interchangeable backends behind the `StateStore` interface ([`src/store/types.ts`](../src/store/types.ts)): the fs reference ([`src/store/fs.ts`](../src/store/fs.ts), layout above), single-file local SQLite ([`src/store/sqlite.ts`](../src/store/sqlite.ts), `WEAVER_STORE=sqlite:<path>`, Node's built-in `node:sqlite` — zero dependencies), and plain Postgres ([`src/store/pg.ts`](../src/store/pg.ts), `WEAVER_STORE=postgres://…`) for hosting the knowledge layer centrally. Postgres stores typed documents as validated `json`, not `jsonb`: `jsonb` decodes `\u0000` and rejects that valid JSON string because a Postgres text value cannot contain a zero byte, while `json` preserves the JSON representation for an exact JavaScript round trip. Its source-key index therefore uses a separate `JSON.stringify(sourceKey)` text column under the `C` collation; the encoding is injective for JavaScript strings, including U+0000, so uniqueness remains atomic without narrowing durable truth. Legacy source-key backfill is serialized with schema initialization, decoded in JavaScript, and tracked by an explicit initialized bit so a genuinely absent key is never repeatedly inspected; PostgreSQL JSON operators are forbidden on the document because asking for one field still parses an unrelated U+0000. Artifact bodies use `bytea`, because Postgres `text` cannot hold a raw U+0000; the store boundary converts strings to and from UTF-8 Buffers, matching filesystem artifact bytes exactly. Exact fleet readback is sorted in JavaScript before comparison because deployment-specific database collations can order the same slugs differently without changing durable content. The revision CAS runs inside a transaction on both database backends — sqlite runs the whole synchronous read→check→write region inside one `BEGIN IMMEDIATE` (FsStore's no-yield guarantee plus cross-process safety from the database write lock); pg re-checks with `UPDATE … WHERE revision = $expected`. Tick exclusion: fs and sqlite record a pid and probe liveness (same-machine by nature); pg uses a session-scoped advisory lock (holder death releases it — that's why only pg has no pid). Source-key uniqueness — two workstreams may never stand for the same external thing — is a store-write contract, not a caller pre-scan: each backend enforces it atomically inside `create` (fs a home-scoped create lock around a fail-loud scan that refuses rather than skip a corrupt sibling, sqlite the `BEGIN IMMEDIATE` write lock around a `json_extract` lookup, pg a partial UNIQUE index), surfacing a `SourceKeyConflictError`. The same contract-test suite in [`src/store.test.ts`](../src/store.test.ts) runs over all three (fs and sqlite unconditionally, pg via `WEAVER_TEST_PG_URL`), including cross-process races spawned as real OS processes — among them two different slugs racing one source key, where exactly one lands. Machine-local things deliberately stay on fs on every backend: printout receipt sidecars, secrets env files, the runner pid lock, the tail's jsonl feed, watch/TUI polling, and the simulated world's outbox.

**Remote-store cost surprise (2026-08-29).** `runLoop` used to implement its
three fleet decisions as independent `listWorkstreams()` plus full `load()`
scans. The production runners poll every five seconds: 35,489,938 document
bytes × two unconditional scans × 720 loops/hour = 51,105,510,720 bytes, or
about 51.1 GB/hour, before useful work. Railway measured 51.87 GB/hour average
database transmit over the active 76-hour window, confirming that predicted
cost rather than a model or compute spike. Four-hour transmit buckets ranged
from 99 GB to 337 GB, making public database egress the dominant infrastructure
charge. The runner now calls `listWorkstreamHeads()` before each logical
decision and keeps
a disposable `(slug, revision) -> doc` cache: only new or changed heads load a
body, absent/unreadable heads evict old bodies, and the post-recovery decision
still performs a fresh head scan so a mutation made moments earlier is visible.
Do not replace this with a time-based cache or merge the logical scans: exact
revision validation and the post-mutation re-scan carry the freshness contract.
The operator UI's `/api/fleet-revision` poll uses the same revision heads plus
typed runner presence to reproduce the full render's hash shape without
calling `loadFleet()`; full documents cross the store seam only for an actual
page render after that cheap hash changes.

**Second remote-store cost surprise (2026-09-08).** After the runner fix the
Railway Postgres still transmitted 30–110 GB/day, and on 2026-09-08 the
workspace's prepaid credit ran out and Railway stopped every service in the
account for three hours. Attribution with `pg_stat_statements` (preloaded in
Railway's Postgres image; `CREATE EXTENSION` once) showed the head poll was
narrow but `SELECT doc … WHERE slug = $1` still ran ~0.6/s: the shared layer's
`listManagedBy()` and `findBySourceKey()` were `listWorkstreams()` + `load()`
loops, and a coordinator pass calls `listManagedBy()` at every start to state
the live count of the streams it manages — one full-fleet transfer (100
documents, 51 MB, some 4 MB each) per pass, over the billed public proxy. Both
are now `StateStore` methods: pg keeps `managed_by_slug` and `status` head
columns beside the document (written by every create/mutate/rename/import,
backfilled once under the schema lock, indexed) and probes the existing
source-key index; sqlite uses `json_extract`; only the fs reference backend
still walks its local files. Rule of thumb for hosted stores: a hot path may
loop over `listWorkstreamHeads()`, never over `load()` — anything that needs one
field of every document is a head column and a backend method.

The same measurement showed the other half of the residual: one tick re-reads
its own document twenty-odd times (`load(slug)` at the top of most engine
helpers, `workstreamStatus`, `deliverManagerNotices`, the coordinator pass),
and a routine's document is large — `daily-engineering-update` was 4.1 MB at
revision 4829 because assignments, passes, wakes and decisions are unbounded
history while only `events` is a bounded tail — so ticks alone moved about a
document a second. `PgStore.load()` therefore keeps a process-local body cache
validated on every read by the row's change token, `xmin` plus the CAS
revision: a hit costs one narrow head read, and any committed write to the row
(a store mutation, a rename, a re-create, an out-of-band UPDATE that forgot the
revision) is a new row version and so a miss. Writes through the store prime
the cache from their `RETURNING` row; callers get a clone so an in-place edit
cannot leak into the next reader. This is deliberately not a time-based cache
and it does not change `load()`'s contract — every call still returns the
current durable document — it only changes what crosses the wire to prove it.
`mutate()` reads the same way inside its transaction: the head first (row-locked
for an arrival), the body only when the token differs from what the process
holds; the arrival's row lock or the checked write's revision predicate guards
the write exactly as before, and a checked write whose body read sees a
different version than its head described reports the revision conflict the
CAS would have. After both changes the fleet's steady state was 45 body reads
against 645 head reads in twelve minutes, from ~1,200 body reads before.
Document growth itself (compacting a routine's finished passes, wakes and
assignments) is the remaining structural item.

**External poolers must preserve session identity.** The Postgres tick lock is
session-scoped, so transaction-mode PgBouncer can hand the next statement a
different backend and silently destroy the exclusion contract. Use a direct or
explicitly unpooled URL for Weaver, or a pooler in session mode. This is why a
GCP execution runner uses Railway's public unpooled URL even when web services
inside Railway use the private application URL.

SQLite artifact bodies use BLOB with the same UTF-8 Buffer boundary. This is load-bearing on Node 22, whose SQLite TEXT binding truncates a JavaScript string at U+0000; a transactionally rebuilt legacy TEXT table preserves existing bytes and prevents that runtime-dependent loss.

The **disposable layer** sits behind explicit coordinator and worker executor seams. A coordinator pass ([`src/coordinator.ts`](../src/coordinator.ts)) is one fresh, hermetic model loop whose entire input is the projection and whose only write path is the revision-checked Weaver tool set; it persists and exits. A worker run ([`src/worker.ts`](../src/worker.ts)) is one fresh regular coding-agent loop over a briefing plus declared inputs. `submit_result` is its only Weaver state API, not its only process capability. Claude sets `persistSession: false`; Codex starts a new thread and never resumes it. Session ids are provenance only.

Where the worker's loop *runs* is a substrate choice behind the `WorkerExecutor` seam ([`src/executor/types.ts`](../src/executor/types.ts), selected by `WEAVER_EXECUTOR`). Four substrates are wired into `selectExecutor`: local Claude `query()` ([`src/executor/localSdk.ts`](../src/executor/localSdk.ts), `local-sdk`, default), a local subscription-backed Codex thread ([`src/executor/codex.ts`](../src/executor/codex.ts), `codex-sdk`), a pinned Pi RPC process with provider-qualified API targets ([`src/executor/pi.ts`](../src/executor/pi.ts), `pi`), and a pinned OpenHands Agent Server container ([`src/executor/openHands.ts`](../src/executor/openHands.ts), `openhands`). Pi and OpenHands relay serializable user/local MCP servers through authenticated host endpoints, so durable credentials and upstream process configuration remain outside the model runtime. The coordinator has its own narrower seam because its zero-outside-tools authority contract is the opposite of a coding worker: `WEAVER_COORDINATOR_EXECUTOR` selects local Claude or Codex, while a provider-qualified `local-sdk:openrouter/...` fallback reuses Claude's tool-restricted protocol in a fresh API home with only the executor-only OpenRouter identity. This does not make OpenRouter a new executor and the hosted profile refuses Claude-family OpenRouter models: every hosted Claude seat remains setup-token subscription-backed. Codex coordination uses a temporary isolated `CODEX_HOME`, disables built-ins/network/web/session history, exposes only the authenticated Weaver bridge, and audits streamed items fail-closed. The worker seam moves only the disposable part: the harness supplies the briefing, environment, submit callback, and — for a declared action — live Pilot supervision. Codex, Pi, and OpenHands currently fail action assignments closed because none exposes that per-call supervision hook. Unknown executor values fail before any pass or attempt starts.

The Pi eval adapter is a thin view over that exact production class. Prime Agent
remains only below the separate harness-eval seam. Both use invocation-local RPC
processes with `--no-session`; Prime goals, autonomous runs, schedules, daemon
state, and transcripts are never read or resumed as Workstream state.

## Actions: touching the real world

There is no channel/adapter layer, and a worker has exactly two lifecycles. A `work` assignment does bounded, reversible work and *proposes* a result; it has the full ordinary Code surface, including the operator's configured MCP servers used freely read AND write — moving a tracker issue's status, commenting, labelling is ordinary work, not an action. An `action` assignment is the single way Weaver directs, authorizes, and verifies one *irreversible* egress to the outside world: sending a message to a person, spending, or pushing/merging/deploying code. The boundary is drawn by consequence, not by which tool or whether the write is remote — a reversible ticket move is bookkeeping and stays `work`. An action's worker has the same normal Code surface as any other; the difference is durable lifecycle: approval before execution, Pilot supervision while it runs, action-only secret values, and deterministic readback afterwards. Normal workers inherit the operator's Code configuration; actions receive an explicit secured copy of the applicable MCP servers so filesystem allow rules cannot bypass Pilot.

The lifecycle enforces "the system cannot grade its own homework":

1. **Gated**: created `state: 'gated'` with a mandatory plain-language `approval_ask`. Routine actions default to `approvalMode: 'pilot-or-human'`; an explicit founder/manual reservation is persisted as `approvalMode: 'human-only'`, which the Pilot auto-approval scan structurally excludes. In either mode the scheduler and worker refuse an action until the matching authority is recorded.
   Every Pilot request uses one shared client. A registered `WEAVER_PILOT_TOKEN`
   is reloaded from the executor-only secret store per request and sent as a
   bearer; it never enters typed state or worker environments. Remote URLs are
   HTTPS-only, redirects fail closed, and tokenless compatibility is loopback-only.
   `weaver pilot-auth-check` exercises that exact path against an authenticated
   204 response before a hosted runner starts.
2. **Executed**: by the worker — or, when a human authored the exact command (`exec.run`), by the ENGINE verbatim with no model in the loop (models judge, humans decide, code executes). Before execution, the engine normally uses `exec.verify` as a postcondition preflight and skips a command whose effect already exists. A deterministic observation whose fresh stdout is itself the result may persist `exec.preflightMode: 'always-execute'`; this suppresses only that pre-execution verifier call, is invalid without `exec.run`, and leaves approval, the one-shot claim, post-execution readback, and unknown-result handling unchanged. The mode does not assert that the command is side-effect-free. Both the command and verifier run in their own POSIX process group: a timeout terminates the complete shell tree before Weaver persists its result, so a command substitution or background child cannot keep acting after the one-shot attempt has settled.
3. **Read back**: `exec.verify` is a shell command the engine runs deterministically; exit 0 is the only thing that can call the effect real. Non-zero, missing, or un-runnable verification is UNKNOWN, never proof that the effect is absent. Worker prose settles nothing.
4. **Adopted**: both the coordinator's `adopt_submission` tool and the human `weaver adopt` override refuse an action whose readback has not run or did not confirm the effect — adoption cannot outrank physics.
5. **Crashed or backed off?** The action is durably failed before it is *read back*, never re-queued — re-inspecting the world is always safe; re-doing the act is not. Confirmation advances it to review; every other readback outcome leaves it failed and raises one deduped blocker for provider/human reconciliation. All dispatch sites reject an action with a prior attempt; any deliberate retry is a new, separately approved action.

## Secrets: names for models, values for shells

Credential values live in `0600` env files under the state dir (global + per-workstream overlays, plus an executor-only file, [`src/secrets.ts`](../src/secrets.ts)). Models see applicable worker-secret names only; executor-secret names and all values stay out of projections. An ordinary `work` Assignment may persist an exact `credentialNames` capability requirement. `create_assignment` validates those names, and `runWorker` resolves the same names again from the execution host immediately before launch, strips every unselected applicable name from ambient child state, and injects only the selected values for that disposable Attempt. The executor request keeps that exact worker-visible subset separate from its host/SDK environment. OpenHands serializes only the subset into a mode-`0600` per-run Docker env file, passes only the path in `docker run`, and removes the file plus its private temp directory immediately after Docker consumes it on success, failure, or abort; it never forwards the host environment wholesale. Missing or invalid selections settle the Assignment failed with one typed blocker before an Attempt or model process exists, so the runner cannot hot-loop a permanently invalid contract. Actions retain their existing applicable-secret scope; executor/model identity credentials remain a disjoint, non-selectable store.

Every worker-secret value — selected or not — joins artifact/submission/tail/error redaction and the shared store's structural refusal boundary. This matters even for an unselected value: a model can repeat text it observed elsewhere, and redaction is an output invariant rather than evidence that a value was injected. Worker stderr is scrubbed before it reaches service logs. OpenHands and Pi keep provider keys behind a host inference proxy and operator MCP credentials behind per-server host relays; their model runtimes receive only random per-run bearers. Pi's extension removes its bearer-bearing environment entries before the ordinary shell is available. Spawned Claude/Codex subscription processes strip ambient provider keys and force their local login paths. The Codex coordinator references `auth.json` through a per-pass temporary-home symlink without reading or copying it, then removes that home. Weaver never mints, extracts, stores, pools, rotates, or cycles subscription credentials. Operator MCP header values are hoisted into child environment placeholders before Claude serializes its MCP config ([`src/mcpConfig.ts`](../src/mcpConfig.ts)).

## The daily digest: operator notification, not an action

Every surface that answered "what needs me?" was pull-only — `weaver watch`, the printout, the operator workspace — so the founder became the fleet's bottleneck without anything saying so: most live child Workstreams sat waiting on a founder card, the Needs-you queue aged into days, and drafted customer replies went unsent for over a week because nobody opened the page that listed them. `weaver digest --post` ([`src/digest.ts`](../src/digest.ts)) pushes that same queue to the operator once a day.

Kernel rule 7 says an `action` is irreversible egress to the outside world, and names "sending a message to a person" as one. The digest is deliberately classified as **operator notification** instead, and the classification rests on four facts rather than on convenience:

- **The destination is fixed by the operator, outside Workstream state.** `WEAVER_DIGEST_SLACK_CHANNEL` lives in the executor-only secret store and is set once per fleet, reloaded per run exactly like `WEAVER_PILOT_TOKEN`. The post uses the fleet's existing Slack bot (`SLACK_BOT_TOKEN`) unless the executor-only `WEAVER_DIGEST_SLACK_TOKEN` overrides it: a fleet that already posts to Slack is not asked for a second credential. No coordinator, worker, policy, or reply can read, name, or change where it goes, so data flow cannot widen its reach (the same reason the printout's recipient is "whoever is at the terminal").
- **No model chooses the recipient or the content.** The text is a deterministic render of typed projections — `fleetNeeds()` (the workspace queue, paused Workstreams excluded), `presentNeed()` headlines, the `/healthz/fleet` verdict (`fleetHealthSnapshot()`: committed output, not heartbeat liveness), `fleetIncidents()`, conclusions, readback-confirmed actions, resolved cards, and pending wakes — redacted with the store's secrets. A summary can neither enter it nor be promoted by it (kernel rule 4), and it answers the five questions without a transcript (rule 10).
- **It acts on no one's behalf.** It tells the operator what already exists in their own fleet. It sends nothing to a customer, a teammate, or a channel other people act on, and approving anything it lists still goes through the normal human act (`weaver approve-action`, `weaver approve`, `weaver resolve`).
- **Its delivery obeys the unknown-result rule anyway.** Each message carries `[weaver-digest YYYY-MM-DD]` (London date). The command reads `conversations.history` for today's marker before posting and does nothing if it is there; a post that errors or times out is read back, and if the marker is still absent the run fails loudly rather than sending again. A missed day is recoverable by hand; a duplicated one would teach the operator to ignore the channel.

It is a printout delivered by push. The line it does not cross is the one rule 7 draws: **posting anything to a team channel or another person remains an action** — gated, Pilot-supervised, and confirmed by readback — however similar the transport looks. What keeps the digest on the notification side is that the operator, not the fleet, chose who reads it: the channel is a standing operator decision (the Erdo fleet posts it beside its daily engineering update, in the channel the team already reads), and nothing a Workstream does can move it or add to what it says.

On the hosted VM the digest has its own `weaver-digest.service` and `weaver-digest.timer` (07:30 Europe/London, `Persistent=true`) rather than riding the runner, because the morning the runner has crashed, wedged, or been refused by its preflight is the morning the operator most needs it. It carries no execution preflight: it launches no model and holds no action capability. It loads the fleet once per run — a once-a-day read, not the hot-path `load()` loop the remote-store cost rule forbids.

## Where each invariant lives

| Invariant | Enforcement |
|---|---|
| Conversation is never the container | `persistSession: false`; the projection ([`src/projection.ts`](../src/projection.ts)) is assembled from typed state only; a fresh pass gets no transcript access at all |
| Projection is bounded, not a work log | [`src/projection.ts`](../src/projection.ts) caps each accumulating section — completed/cancelled assignments are counted not enumerated, older adopted deliverables and retired decisions collapse to a lineage tail, and standing rationales are excerpted — so a routine can run hundreds of cycles without the prompt growing linearly. Nothing is discarded: the full history stays authoritative in `[i]`/printout. A decision is standing only while it binds — `close_decision` retires a finished course (status `closed`), and a step or cycle advance is `progress` on the same standing course rather than a new decision (see "Decisions are commitments; progress is position" below), so cycle history does not masquerade as standing commitment. Review boundaries are excerpted like rationales, and pass boundary events carry a 300-character excerpt while the PassRecord keeps the whole summary. The policy block keeps doctrine statements verbatim, caps active learned policies at the 30 with the most intervention-free evidence, and excerpts effect descriptions and mechanisms behind the read-only `read_policy` tool. Proved by [`src/projection.test.ts`](../src/projection.test.ts) and [`src/policies.test.ts`](../src/policies.test.ts) |
| A step is progress, not a decision | `record_progress` ([`src/coordinator.ts`](../src/coordinator.ts)) writes `Decision.progress` on a standing course through the same revision-checked `change()` path as every tool; it refuses a retired course, a backwards `(cycle, step)`, awaited ids that are not live (`liveOrganizationalItemLabel`, shared with wake courses) and basis ids that are not results (`progressBasisLabels`, beside the conclusion gate), and an identical call writes nothing. It creates no decision and can adopt, complete or conclude nothing. Coordinator decision text is capped at the schema and in each handler. Proved by [`src/coordinator.test.ts`](../src/coordinator.test.ts) |
| Revision-checked writes | `mutate(slug, expectedRevision, fn)` in [`src/store.ts`](../src/store.ts); every coordinator tool call advances a tracked revision, and any external arrival in between makes the next tool call fail with an instruction to finish the pass |
| A finish that conflicts is not a completion | `finish_pass` marks the pass `finished` ONLY after its own revision-checked write lands; a write that loses to a concurrent arrival records the pass `conflicted` (a distinct outcome — [`src/coordinator.ts`](../src/coordinator.ts) `passOutcome`), never `completed`. Steering/directions are consumed in that same write, so a conflict rolls their consumption back too; the pass restores an immediate reconciliation wake and does NOT count toward the three-failures human card |
| Single-flight coordinator | `lease` field on the doc; a second pass refuses to start while a live lease exists |
| No pass silently stays 'running' | Beyond the expired-lease recovery, an orphan sweep in [`src/engine.ts`](../src/engine.ts) repairs any `running` pass with no LIVE lease naming it (marks it `no_finish`, restores a wake). `passIntegrityWarnings` ([`src/ui/inspect/model.ts`](../src/ui/inspect/model.ts)) surfaces impossible provenance (a `completed` pass with no summary) rather than rewriting history |
| Adoption ≠ completion | Workers set `state: awaiting_review, adoption: proposed`; only the coordinator's `adopt_submission` sets `accepted`, verifying artifact integrity and pinning `contentHash` at that moment |
| Adoption gates downstream work | `runnableAssignments` ([`src/engine.ts`](../src/engine.ts)) releases a dependent assignment only when its upstream is `completed` AND `adoption: accepted` — the exact condition `worker.ts` uses to inject a dependency's artifact, so a runnable worker always receives every input it expects. A rejected upstream (`reject_submission` leaves `completed` + `rejected`) or a cancelled one never auto-satisfies: `create_assignment` refuses dependencies already settled without acceptance, while `flagImpossibleDependencies` raises one deduped integrity `blocker` if an existing edge later becomes missing, failed, cancelled, rejected, or superseded. Re-pointing around absent input remains an explicit coordinator act, never a scheduler inference |
| Capability is not authority | Every assignment has the normal Code surface — including the operator's MCP servers used read AND write, so keeping the systems a brief names in sync (a tracker issue's status, a comment, a label) is ordinary reversible `work`, no approval or allow-list — but only `submit_result` can propose Workstream state. A work Assignment's `credentialNames` is an explicit capability requirement, not an authority grant: it selects only values already applicable to that workstream and cannot reach executor identity. The line is consequence, not tool: only *irreversible* egress (sending to a person, spending, pushing/merging/deploying) is a separate typed `action`; drafts and sends remain separate lifecycles. The coordinator has no external tools at all (`tools: []` + the weaver mutation server): the seat that decides reads the world only through work it dispatched and adopted — see [intake.md](./intake.md) |
| Authority revalidated at egress | Sends execute in the engine ([`src/engine.ts`](../src/engine.ts)), not in any model run: approval, pinned-hash match, and artifact integrity are re-checked, then a single revision-checked **egress claim** flips the interaction `approved → sending` — the one linearization point against human rejection. A reject that crosses first leaves it un-`approved` (no call); a reject that crosses after finds `sending` and is refused (`rejectSend`), so a real effect is never overwritten with a false `rejected` |
| Unknown result → readback, never re-send | `WEAVER_SEND_UNKNOWN=1` simulates a crash after egress; the interaction goes to `unknown` (a crashed `sending` claim is treated the same) and a later tick resolves it via `providerLookup` — re-queueing happens only when that provider-specific lookup positively proves no record. Actions are stricter because an arbitrary verifier's non-zero exit cannot prove absence: crashed or infrastructure-backed-off actions are held `failed`; only exit 0 advances to review, while non-zero/missing/broken verification raises one deduped reconciliation blocker. `runnableAssignments`, `executeHumanActions`, and `runWorker` all refuse a prior-attempt action, so a retry requires a new action and approval. The simulated provider keeps an append-only ledger ([`src/world.ts`](../src/world.ts)) separating invocation *attempts* from *effects*, and the interaction id is an idempotency key: at most one external effect exists per interaction however many attempts occur |
| Repo egress is deconflicted (invariant 8 across the git-repo seam) | Weaver conflict-checks its own state but historically stopped at the repo boundary — the roadmap-intake routine once opened PRs into files a teammate's open PR (#1993) was actively editing. Before an action does an irreversible repo egress (`gh pr create`/`gh pr merge`/`git push` — `isRepoEgressAction`), `guardRepoEgress` ([`src/engine.ts`](../src/engine.ts), wired at BOTH execution sites) judges the shared external state it is about to write into, with two postures for two different facts (`src/deconflict.ts`, proved by [`src/deconflict.test.ts`](../src/deconflict.test.ts)). A deterministic action's literal `exec.run` is authoritative: read-only `gh pr view/list/api` probes do not acquire repo-egress credentials or enter this gate. Model-driven actions have no literal run, so their durable PR/remote-ref verify remains the proxy for the write performed inside the disposable run. **File overlap with another OPEN PR is REPORTED, never blocked** (`detectRepoCollisions`): separate refs are ordinary parallel development, git merges them, and a real textual conflict surfaces at merge time — so the overlap is recorded on the workstream (one deduped event keyed on action id + sorted contended files) and the action ships. **A push target whose own PR has MERGED or CLOSED is HELD** (`checkStrandedPush`): the commits are already in the trunk and the PR is done, so the push lands a commit no PR carries and no reviewer sees — a workstream once pushed a follow-up refactor 43 minutes after its PR merged and it had to be re-homed by hand. The held action stays `queued`+approved and the stream is woken with the instruction (`strandedPushGuidance`: fresh branch cut from the current base, new PR, never re-push the settled ref, never reopen the settled PR); unlike an overlap this hold does not clear on its own, because a merged PR never reopens — reconcile, don't re-write (invariants 7 & 8). The push target comes from the world (the checkout's branch) unless the command names a destination ref explicitly (`pushTargetBranch`). Both checks **fail OPEN on tooling failure** (no `gh`, not a repo, detached HEAD → no verdict, never a throw — a broken `gh` must not wedge the fleet), and the settled-branch check logs its abstention rather than passing it off as clean; both **fail CLOSED only on a fact actually read** — the same asymmetry as an unknown send |
| Readback observes, never acts | `verifyAction` refuses unless the action was approved (human/pilot) **and** has a recorded execution attempt, and loads no secrets until that gate passes — a gated/unapproved action's model-authored `exec.verify` shell cannot run as a credentialed backdoor. Making that shell structurally unable to *create* the fact it observes needs a read-only execution substrate (the `WorkerExecutor` seam); until then the post-approval-only gate is the documented trust boundary, not a claim that arbitrary verify shell is read-only |
| Replies are untrusted | A reply wakes the workstream and is listed as unevaluated input; only `evaluate_reply` (a coordinator act) turns it into a result |
| Summaries cannot mutate truth | `finish_pass` stores the coordinator's summary on the pass record; nothing reads it back into state — the projection is rebuilt from typed collections every pass |
| Wakes are stored data | [`src/clock.ts`](../src/clock.ts) + the `wakes` collection; `weaver advance 5d` moves a persistent offset and `weaver tick` discovers what became due — no process ever sleeps. Every new organizational wake names the exact standing decision, live assignment, active interaction, or open attention item it serves. A coordinator may revision-check cancel it only when cited typed facts directly close or supersede that stored course; unrelated real facts and prose are refused, while reason/basis ids remain on the cancelled record. The projection shows a bounded head and count while `list_cancellable_wakes` pages every remaining exact id. Fired delivery and harness-owned infrastructure, execution-safety, immediate-arrival, and wall-time wakes cannot be cancelled individually; validated workstream conclusion stores one fixed pass reference on each retired wait rather than duplicating its summary/evidence |
| Printout deltas survive waits | `mutate()` centrally diffs every typed collection into an immutable sidecar per revision, including eventless writes and exact intermediate before/after values. The sidecar is committed before the matching head and a delivery acknowledgement lives outside organizational revision state. Fleet scope also journals global policy mutations. Authoritative claims are rebuilt from assignment, deliverable, interaction, pass, and action-readback state; the bounded run tail can add best-effort “looked at” observations but can never prove an external effect |
| Conclusions cannot self-certify | `conclude_workstream` resolves every cited id through `conclusionEvidenceLabels`: only an adopted deliverable, a readback-confirmed action, or a human steering directive is accepted — a coordinator-authored decision is refused, so a pass cannot write a decision and cite it to conclude its own workstream. Legitimate non-action closure cites the human steering that authorized it. The durable conclusion stores those ids, never free-form evidence prose. (Criterion-by-criterion typed evaluation against `successCriteria` is a deliberate follow-up.) |

## Decisions are commitments; progress is position

Kernel rule 5 says decisions are the commitment layer, not the record of all work, but until September 2026 the schema had nowhere else to put a routine's position. A coordinator that wanted the next pass to know "we are on step 3 of cycle 22" could only say it in prose, and the only prose that survived into the projection's standing section was a decision. So coordinators used decisions as a step log: over 30 days of production passes, 1,635 decisions were recorded, 73% of them were superseded with a median life of 35 minutes, 501 supersessions carried a counter in both titles ("step 2 → step 3", "Cycle 21 → Cycle 22", "Phase 2b-8 → 2b-9 → … → 2b-36"), and one supersede chain reached 72 decisions. The prompt blessed it — rule 6 told the coordinator to record a standing decision whenever a periodic check had no narrower course — and every one of those decisions carried a rationale whose median was 2,213 characters, because the decision was also carrying the evidence and the handoff note.

The fix adds no new noun. `Wake.organizationalCourseId` already names a standing decision as "the course", so the course is where its position lives: `Decision.progress` is a `CourseProgress` (cycle, step, a short label, the live ids it awaits, the result ids it rests on, the next move, and when the cycle started), overwritten in place by `record_progress`. Superseding is reserved for when the commitment itself — the what or the why — changes, which is what lineage is for. The split has teeth in both directions. Progress is position, never authority: it cites typed facts (awaited ids must be live assignments, active interactions or open attention items; basis ids must be adopted deliverables, readback-confirmed actions or evaluated observations/replies) and cannot adopt, complete, or conclude anything, so a stale or wrong progress record can mislead a coordinator about where it is but never about what is true. And because it is not a decision, it cannot become conclusion evidence or a supersession basis for a wake.

The projection renders one line under each standing course that has progress, marking any awaited id that has since settled, and names any supersede lineage with five or more supersessions inside the last 24 hours as a step log. That nudge reads only lineage links and `decidedAtVirtual`, never titles, so it cannot be steered by how a decision is worded; on the production store 74 of 379 supersede lineages would have tripped it at some point. The caps on coordinator text (title 200, rationale 1,500, review boundary 300, close reason 600, progress label 120 and next 400 characters) refuse rather than truncate, with a message that sends evidence to cited deliverables and steps to `record_progress`; they apply at the tool schema and again in each handler, since the handler is the write path. Legacy oversize decisions still load and render excerpted, and human-authored decisions are never capped. Printouts journal every progress update as a decision field delta, the `course.progress` event keeps the tail readable, and `weaver status` and the inspect view show the position beside the course.

## The tick, the runner, and the dashboard

`weaver tick` is the entire runtime: recover crashed attempts → resolve unknown sends by readback → execute approved sends (egress checks) → execute human-authored actions → surface any assignment stuck on a dangling dependency → run queued workers whose dependencies settled (upstream `completed` and `accepted`) → run action readbacks → coalesce due wakes into one coordinator pass → repeat until quiescent (bounded). Wake delivery is at-least-once and coalesced: firing marks the wakes, and anything lost to a crash is repaired by the next reconciliation because the underlying facts (submissions, replies, steering) are in typed state regardless.

Ticks are **cross-process exclusive** per workstream (an ownership-marked pid lock in the filesystem backend; a session advisory lock in Postgres) so a resident runner plus a manual tick can never double-dispatch a real-world act. Filesystem store writes, the resident-runner singleton, filesystem global-policy writes, and printout checkpoint writes use the same process-lock primitive. Only `ESRCH` proves a pid absent; `EPERM` and unknown probes fail closed. Complete owner metadata becomes visible atomically, stale cleanup unlinks the exact unique owner it inspected, and release cannot recursively delete a successor's lock. `weaver run` polls cheap durable heads, but dispatches an active workstream only once per observed revision or when a typed no-write trigger becomes due (time wake, expired lease, orphaned attempt, approval-service retry, or coordinator-host failover). A disposable revision-keyed body cache and dispatch watermark hold no truth: restart the runner and every active stream gets one recovery reconciliation from the store. Cross-document manager-notice keys also select a concluded child exactly while delivery is missing. A runner concurrency slot remains owned until the exact tick promise settles, and only a successful non-lock-skipped tick marks its starting revision reconciled. SDK hangs are bounded at their real worker/coordinator call sites; a coarse whole-tick timer cannot abort the underlying operation and must never free only the accounting slot while the process and tick lock remain live. When the loaded checkout becomes stale, polling stops before another dispatch and existing ticks use the same bounded exit drain as an operator-requested shutdown — source replacement never creates an unbounded second drain path.

Resident runners also publish a TTL heartbeat through the `StateStore`, separate from Workstream revisions and the machine-local pid heartbeat. Optional `WorkstreamCore.executionPolicy.coordinatorRunnerOrder` is the human-owned physical preference for coordinator passes: the first listed runner is primary while its shared heartbeat is fresh, and a later runner may claim only when every earlier runner is either stale or seatless — presence carries each runner's coordinator seats (its configured executor/provider/model chain), and a live runner whose every seat is capacity-parked on that Workstream yields the claim, because a host that cannot launch a pass must not hold one while a later host could. Eligibility is checked before wake consumption and again inside the revision-checked lease/pass claim; the lease and PassRecord pin the claiming runner. Omission preserves fleet-wide coordination. The policy does not wrap the tick, sends, engine actions, or workers: exact `Assignment.runnerId` placement remains stronger and independent, so machine-bound work can still execute on another host while coordination stays on its preferred seat. Presence is an expiring operational observation, never a worker definition or an authority grant.

Runaway safety is a **rolling physical-time execution guard**, not spend management. Before every coordinator or model-backed worker claim, Weaver counts typed `PassRecord.startedAt` plus non-engine `Attempt.startedAt` values in the Workstream's rolling window (default 30 starts/hour). The check and start record share the same revision-checked mutation. At the limit, intended assignments and organizational wakes remain pending behind one deduplicated `wall_time` wake; no human attention opens, `weaver advance` cannot bypass it, and work resumes automatically when enough starts expire. All terminal outcomes and legacy model attempts count; deterministic engine commands do not. Lifetime pass totals and SDK dollar estimates remain diagnostic history only. Legacy cap fields load but never gate, and old engine-generated dollar cards retire on reconciliation. This corrects the original finite-autonomy proof: once routines became indefinite, any lifetime cap guaranteed the death of healthy work and an SDK estimate was never provider billing. Physical start timestamps assume normally synchronized host clocks across a shared Postgres fleet; clock skew can delay recovery safely, while exact database-time semantics would require a wider backend contract.

Pause is a durable per-workstream lifecycle transition, not runner memory. `weaver pause <slug>` pauses one stream; `weaver pause` applies the same revision-checked transition independently to every stream active at that invocation. Already paused and done streams are preserved, and streams created later start active — there is intentionally no ambient fleet flag or cross-workstream transaction. Pending assignments and wakes remain typed state, and `weaver resume <slug>` reactivates one stream without resuming any model session. Runner polls and manual ticks skip paused streams; an in-flight tick re-reads status before each worker, coordinator, and egress boundary. A disposable step already running may finish and record its result, but no next step starts after the pause lands.

Provider capacity is a separate control path. A coordinator or worker result that reports plan/session/rate limiting, overload, or invalid authentication updates executor/provider/model-scoped `WorkstreamDoc.capacity` and records a typed infrastructure-backoff wake; it does not fail intended work, immediately retry, or contribute a failure strike (the physical model start still counts toward rolling execution safety). Capacity state, not pass-summary or wake-reason prose, controls dispatch and recovery. Only the affected target is parked: `pickCoordinatorTarget` walks the deduped coordinator chain (`WEAVER_COORDINATOR_FALLBACKS`, or the legacy single-fallback pair while it is unset) to the first seat with no active wait, while workers route each queued assignment from its typed profile/modalities through reviewed targets in preference order, then the configured seat, then the operator's explicit `WEAVER_WORKER_FALLBACKS` capacity ladder (the profile vocabulary and its rationale: [docs/execution-profiles.md](./execution-profiles.md)). *Automatic* cross-executor preference remains closed until that execution policy is durable Workstream state — a process-local setting would make model choice a Postgres tick-lock race — but the ordered ladder is the operator's own machine config, the same trust class as `WEAVER_EXECUTOR`, so its seats may name any executor; `capacityPresentation` calls the coordinator BLOCKED only when every chain seat holds an active wait, and the degrade-don't-park wake fires whenever any seat other than the one that just failed is free. `WEAVER_RUNNER_EXECUTORS` is each process's actual launchability: capability gates the first capacity-available target, and the revision-checked attempt/lease claim revalidates it. Missing capability leaves work for a capable heterogeneous runner instead of making the next preference eligible. One limited route can advance to an available fallback without parking unrelated work. A shared role-aware projection labels provider backoff and process-local executor waits separately: the latter has no invented retry timestamp. Overdue, unconfigured, and fallback-covered records are history/degradation, not a parked stream. Authentication raises one deduped `kind: 'capacity'` card immediately; usage/session/rate/other failures wait 12 consecutive backoffs before escalating. Weaver retries at the earliest future provider reset (or a bounded fallback), performs a model-specific probe only for local Anthropic SDK waits when Claude credential-file metadata changes, and accepts an explicit billing-neutral `weaver capacity retry` after provider-side settings change. There is no periodic model polling and non-Claude waits are never probed through Claude. Only metadata is observed — Weaver never reads or copies a credential. No process or SDK session remains alive while waiting.

**A seat parked for one workstream is parked for the fleet.** A limit on one exact executor/provider/model target is a fact about the account behind that seat, not about the workstream that happened to discover it, and the production store proved that treating it per-stream was the fleet's dominant waste: over the 30 days to 2026-09-21, 62% of coordinator passes (5,411 of 8,693) were capacity backoffs, 96.4% of those started while another workstream already held an active wait on the same target, and 91.6% had no success on that target in between — the launch only rediscovered the limit (glm-5.3 backed off 405–496 times a day with no success for four days). Worker attempts had the same shape: 739 of 865 backoffs. The cost of believing the shared wait is small: only 2% of successful passes (66 of 3,252) started under one, with a median extra wait of 13 minutes. So discovery is now shared, with the mechanism built entirely from typed state:

- *The fleet view is derived, not stored.* `fleetSeatView` (capacity.ts) is a pure function over the documents the runner's revision-keyed cache already holds, so it costs no store reads. Per exact target it returns the latest-detected **active** first-hand wait from any active workstream, unless a later success anywhere refutes it: a `completed` PassRecord or an ended, non-crashed Attempt with no infrastructure whose end falls after the wait's `detectedAt`. Waits of kind `other` (safety walls, network drops, provider 5xx) and `auth` (this host's credential) stay per host — a laptop that lost its network or login must never park a healthy VM — and legacy waits naming no executor/provider name no pool. Borrowed copies are never sources, so copies cannot keep one another alive after their source clears.
- *The tick adopts before it launches.* The runner passes `tick(slug, { fleetCapacity })`; `parkOnFleetCapacity` (engine.ts) runs before the worker gate and again before the coordinator gate, modelled on `parkIfExecutionLimited`: a dry run decides whether anything would change, and the change is re-derived inside `arrive` against the current revision. For every seat a launch would use — each queued candidate's worker chain, and the coordinator chain while a pass is due — that the fleet holds and this stream does not, it copies the wait into `WorkstreamDoc.capacity` with `InfrastructureWait.observedIn` naming the source workstream. The copy keeps the source's `detectedAt`/`retryAt`, keeps the stream's own backoff count, raises no attention and writes no PassRecord or Attempt, so nothing counts toward spend, strikes, or the rolling execution guard. It never overwrites the stream's own active wait, never re-borrows an observation the stream already holds (so `weaver capacity retry` of a borrowed wait is honoured), and never borrows a wait its own later success refutes. Every existing reader then works unchanged: `pickCoordinatorTarget` sends the pass straight to a free fallback (no doomed primary pass, no separate "continue on fallback" pass), worker routing picks the free seat, presentation and runner failover see the park.
- *One deferral wake, never a pass reason.* When a role's whole chain is parked and a borrowed wait is part of it, the stream keeps exactly one pending harness-owned `Wake{ time: earliest borrowed retryAt, infrastructure: <that wait> }`, moved rather than duplicated. It exists only so the dispatch signature changes at that instant. Whether to create it depends on the ticking host's chains, but when it fires and when it retires must not: runners with different configured chains share the document, and if one host retired or moved a wake the other had just written, each write would re-dispatch the other forever. So the wake always sits at the earliest active borrowed retry in the document and retires only when no borrowed wait is active. Due organizational wakes stay pending, and `dueWakes` never fires the deferral wake or this stream's own worker retry permit on a borrowed-parked seat, so neither becomes a wasted coordinator pass. For the same reason the quiescence backstop, the orphaned-pass sweep, the legacy-card migration and fleet-health dormancy never count it as the stream's next check. Coordinator finalization deliberately does not retire it as a covered retry: the park re-derives it, and retiring a worker deferral after an unrelated pass would only make the next tick recreate it.
- *Release follows the view that lent it.* `fleetRecoveredSlugs` now combines this host's recovery ledger with success evidence from the cached documents, so a success recorded by any host releases parks everywhere. A borrowed copy is released only when the fleet view no longer holds that wait or a newer one — refuted, cleared, or retried at its source. Releasing copies on the host ledger instead would free a copy the view still lends, and the next tick would borrow it straight back.
- *An expired wait gets one probe, not a herd.* Every stream deferred on a wait falls due at the same retryAt. When a target's latest wait has expired and nothing has refuted it, the runner admits at most one in-flight tick whose next launch would use that target (`fleetLaunchTargetKeys` predicts it with the tick's own park and seat choice); the others are left unacknowledged so the next poll re-evaluates them. The probe either records a new wait — the others then re-defer durably to the new retry with no pass — or succeeds, and the others launch. The hold ends when the probe's tick settles or after `PROBE_HOLD_MS` (5 minutes) with no newer wait for that exact target, whichever comes first: a rejected launch writes its backoff within seconds, as the attempt or pass ends on the limit error, while a worker probe that got through can run for its whole 40-minute wall. Five quiet minutes therefore means the seat is serving, and the others are admitted while the probe keeps running. The probe map is runner memory: admission control, not truth, with no schema of its own. After a crash the worst case is one herd bounded by the concurrency cap.

A direct `weaver tick` receives no fleet snapshot and keeps today's per-stream behaviour.

Runner placement is an orthogonal Assignment constraint, not another routing or authority system. Optional `Assignment.runnerId` names the exact `WEAVER_RUNNER_ID` allowed to claim that intended work. Both deterministic-engine and model-backed lanes check the placement before preparation and again inside their revision-checked attempt claim; a mismatch leaves the Assignment queued with zero mutation, while a matching Attempt pins the actual runner ID beside executor/provider/model. Omitted placement preserves fleet-wide scheduling. `WorkstreamCore.assignmentRunnerId` is the durable resource constraint for a stream whose every Assignment depends on one host: `create_assignment` inherits it and refuses an override, while the human `weaver placement` arrival atomically updates only queued/gated Assignments with no live Attempt. Arrival serialization closes the claim race — a prior claim is already running and stays put; a later stale claim loses its revision check. Clearing the binding removes placement from the same safe pending set. Coordinator passes remain fleet-wide because they are controllers, not Assignments. Immediate PID crash detection trusts `runnerPid` only when the Attempt belongs to this runner (legacy records retain the former behavior), so equal PIDs on two hosts cannot manufacture an orphan. `WEAVER_RUNNER_PLACEMENT_ONLY=1` requires an explicit ID and narrows matching to explicitly placed assignments; the resident loop refuses this partial posture. The matching `weaver tick --engine-only` path is structurally smaller than a normal tick: action crash/legacy reconciliation, already-approved deterministic `exec.run`, and readback only — no sends, Pilot decisions, model workers, or coordinator.

A local safety wall is not provider evidence. Every worker is told the sleep-aware 40-minute hard wall up front and reserves its final ten awake minutes for `append_section` plus `submit_result`; optional investigation, extra captures, and polish stop at minute 30. Ordinary complete submissions reject only blank content: length cannot distinguish a placeholder from a legitimate one-byte flag or byte-exact fixture, and adoption is the coordinator's literal acceptance judgment. If the hard wall still lands after one or more substantial appended sections but before final submission, the harness proposes those sections as a typed `checkpoint` deliverable and records `wall_timeout_checkpoint` on the disposable Attempt. The coordinator can read and reject that candidate while dispatching only the missing work, but `adopt_submission` structurally refuses it: a partial transcript or draft can never become authoritative merely because a process timed out. With no substantial checkpoint, the attempt remains a failed `wall_timeout` and immediately wakes a fresh coordinator to retry, split, or revise the intended assignment. Neither outcome parks the OpenAI/Anthropic pool or produces a false provider-capacity headline. A coordinator wall remains an infrastructure backoff because the controller itself made no work judgment and must be retried without striking the Workstream. This source-sensitive distinction is load-bearing: both SDKs can surface the local abort as generic “operation aborted” text.

`ProviderCapacityObservation` is glanceable, non-authoritative telemetry distinct from a backoff. Claude subscription `rate_limit_event` messages can report a plan window, utilization, and reset even while a run remains allowed; those observations are persisted at pass/run finalization and aggregated in the fleet header for 30 minutes. Missing or stale data means unknown. Executors without an equivalent event (including the current OpenHands/Kimi path) never receive a synthetic percentage from tokens, SDK costs, or the rolling execution guard. Observations are not included in the coordinator projection: they cannot make the model self-budget, gate dispatch, grant authority, or claim recovery.

Anthropic's announced separate monthly Agent SDK allowance is currently paused; Agent SDK usage continues to draw from shared Claude plan limits. Supported continuations are waiting for reset or the operator explicitly enabling usage credits/a bundle with Anthropic-side spend controls. That provider billing decision is deliberately outside Weaver: it waits and explains recovery, but never opts into spend or selects another account. Shared production automation belongs on a deliberately designed Platform API deployment, not Weaver's single-operator subscription path. Public contract and official sources: [`docs-public/claude-capacity.md`](../docs-public/claude-capacity.md).

`weaver watch` is the interactive dashboard (Ink): the needs-you queue first — every item answerable with one keypress (approve/reject/resolve/steer), approval cards in plain language with the actual commands extracted from the briefing — then workstreams and `↻ ROUTINES` (tag `routine`) with next-run times. Everything rendered is a projection of typed state: no transcript parsing, no idle-timer liveness guessing, and an unreadable doc renders as a loud failure, never an empty screen. Human keypresses call the same first-class mutations as the CLI ([`src/humanActs.ts`](../src/humanActs.ts)) so the two write paths cannot drift; a worker failing without a submission goes back to the coordinator to retry and reaches the human only if the coordinator judges it truly stuck.

`weaver inspect [slug]` publishes the read-only browser surface. [`src/inspect.ts`](../src/inspect.ts) is only the store/redaction/publication boundary; pure typed view models and React server-rendered pages live under [`src/ui/inspect/`](../src/ui/inspect/), with Tailwind v4 compiled into each self-contained HTML file. There is no browser server, client-side state authority, or mutation route. The fleet projects Workstreams into Needs you / In motion / Waiting / Ready; each Workstream projects Assignments into Planned / Working / Review / Accepted, where Accepted requires `completed` plus `adoption.state === 'accepted'` and Attempts remain nested provenance. Primary copy maps those kernel terms to plain language and keeps storage ids in Technical details. Human direction is read from typed `steering`, with its physical timestamp and only the provable waiting/read/withdrawn state; decisions retain the organizational clock. Every static page names its revision and generation time. Page generation has no read-receipt semantics. Only the printout delivery checkpoint below can advance an exact catch-up boundary.

The dashboard owns the embedded runner's lifetime as well as its alternate screen: `q` aborts future polls, restores the terminal, and exits the disposable process so a non-abortable in-flight SDK call cannot pin it. The singleton lock is released by the process-exit handler only when that process is actually gone; durable attempt recovery handles interrupted work on the next tick.

Uppercase `P` opens the same selection-scoped HTML printout available as `weaver printout [slug]`: a selected item or workstream scopes it locally, while the fleet header scopes it across all workstreams and the global policy store. Preparing the report is a read; Weaver atomically writes a unique self-contained archive plus the derived `WEAVER_HOME/printouts/index.html` hub, hands that immutable file to the OS browser, and only then advances the monotonic sidecar cursor. A failed handoff keeps the window pending while leaving the saved page discoverable. The cursor never changes the Workstream revision, while concurrent arrivals beyond the frozen revision remain for the next report. Visual work pages link to the hub. Each archive is a narrow, long-form engineering document with all selected workstreams and exact organizational timelines in normal document flow; SDK dollar-estimate fields are filtered from the operator report, and no card, accordion, or disclosure interaction is required to read the remaining record. The browser page copies the complete plain text with its button or uppercase `C`. Lowercase `p` remains pause. `--text` preserves the stdout-flush delivery path for scripts. Legacy gaps are labeled; complete sidecar windows are exact.

## How needs-you cards close

An `AttentionItem` is addressed to the human, so the paths that close one are deliberately few, and each stamps who did it in `resolvedBy`:

- **The act the card asks for.** Approving or rejecting a gated action, approving a send, steering, or `weaver resolve` (with or without a note) — all human acts in [`src/humanActs.ts`](../src/humanActs.ts), each counted once in `spend.humanInterventions`.
- **The coordinator**, with `withdraw_attention` / `resolve_attention`, when steering answered the card or events made it moot. Bookkeeping, never judgment-taking; stamped `coordinator`.
- **Pilot**, when it approves the gated action the card was raised for (`pilot`).
- **A declared external fact the runner reads back** (`engine:readback`). `raise_attention` takes an optional `resolves_when` list (at most five typed `ExternalFact`s): `github_pr_state` (`owner/name`, PR number, `MERGED`/`CLOSED`) or `sentry_issue_status` (org, short id, `resolved`/`ignored`). The coordinator declares one only when the ask genuinely stops mattering once the fact holds ("merge or close #2686?" is moot once #2686 merges). The runner's `sweepAttentionReadbacks` ([`src/attentionReadback.ts`](../src/attentionReadback.ts)) runs off the poll loop, one sweep in flight, over the runner's revision-validated document cache — paused and idle streams included, because nothing ticks them — so it never reloads the fleet. It batches one GraphQL query per repository with the host's GitHub App READ token for that exact repository, and reads Sentry's `shortids` endpoint with the executor-only `WEAVER_SENTRY_READ_TOKEN`; both stay in the runner process and never reach a worker, and a worker-visible `SENTRY_AUTH_TOKEN` is never used. Reads are throttled in runner memory by card age (5 minutes in the first hour, 15 in the first day, hourly in the first week, then every 6 hours; nothing persisted, a restart reads once more). A card closes only on an exact typed answer: an OPEN PR, a missing App or token, an HTTP error, or an unknown answer writes nothing. The close is one revision-checked write against the cached revision the decision was made on — a card closed concurrently is a no-op, and only a lost race costs one `load()` — which records `resolution.evidence` (the fact, what was observed, the provider URL), emits `attention.readback_resolved`, and wakes the stream if it is active, since the fact may be exactly what it was waiting on.
- **Capacity recovered** (`engine:capacity-recovered`), from typed state only. A capacity card declares `capacity_target_unblocked` (role + exact executor/provider/model) when raised; older cards yield the same fact through `refId` → the backoff wake's typed `InfrastructureWait`, never through the summary text. The card is moot when (i) that exact target has succeeded after the card was created — the fleet recovery ledger or any cached pass/attempt that reached the provider, whether or not the stored wait is already due and whether or not the stream is paused — or (ii) the card's own workstream has since completed a coordinator pass (coordinator role) or had a worker submission stand (worker role) on ANY target: the work is flowing again. Rule (ii) also fires at the success sites themselves (`runCoordinatorPass` finalization, `finalizeWorkerRun`). `doc.capacity` backoff entries are untouched either way: routing still knows the limited pool is limited. The same logic governs raising: a limited seat whose role can continue on a free fallback (the coordinator's degrade-don't-park seat, a worker target without an active wait) opens no NEW card — it would be moot the moment the fallback completes, and every later retry of the limited pool would flicker another card onto the queue. An already-open card is still refreshed.

`capacity_target_unblocked` is harness-owned: `raise_attention` refuses it, as it refuses an unknown kind or a malformed repo, PR number, or Sentry short id, and it refuses the whole list rather than dropping one fact silently. Every system actor (`pilot`, `coordinator`, `worker`, `fleet-capacity`, `capacity-probe`, `execution-safety-migration`, and any `engine:*`) is excluded from the human-intervention metric by `isSystemActor` in [`src/stats.ts`](../src/stats.ts); none of these paths increments `spend.humanInterventions`.

Prose never binds a card. A summary that mentions a PR is not a declared fact — measured on the live fleet, 14 of the 19 open cards that cited a PR cited a merged one only as background to a still-live ask. For legacy cards, `weaver attention-hints [--apply]` ([`src/attentionHints.ts`](../src/attentionHints.ts)) reads back PRs cited by an explicit `github.com/<owner>/<repo>/pull/<n>` URL, an `owner/repo#n`, or a bare `#n` when the workstream names exactly one repository (in its constraints or through its assignments' `readDirs` origins), and for each MERGED/CLOSED PR posts ONE idempotent Observation (`attention-hint:<attId>:<repo>#<n>:<state>`) to the owning workstream. The coordinator evaluates it and decides whether to withdraw the card (kernel rule 9); the command never closes anything, and without `--apply` it only prints.

## Managed Workstreams: flat, not a tree

A coordinator can delegate a genuinely separate outcome to a brand-new Workstream it manages ([`src/managedWorkstreams.ts`](../src/managedWorkstreams.ts), wired to three MCP tools in [`src/coordinator.ts`](../src/coordinator.ts); delivery in [`src/engine.ts`](../src/engine.ts)). This is the first cross-workstream relationship in the codebase, so it gets its own invariant mapping rather than folding into the table above.

**Kernel rule 1 (identities stay distinct; management is one hop, never a tree of authority).** `WorkstreamCore.managedBy` is a single pointer set once at creation — the manager's own doc stores no mirrored "manages" array; `listManagedBy(managerSlug)` (store.ts) derives direct children by a single-level scan. Nothing anywhere resolves a chain: `inspect_workstream` refuses unless `managedBy.slug === callingSlug` (one hop only), and `listManagedBy` never recurses. The recursion test (`src/managedWorkstream.test.ts`) proves it directly — A manages B manages C, and `listManagedBy('A')` never surfaces C. `status.ts`, `watch.ts`, and the inspect view model render this as one-line labels (`Managed by: <slug>` / `Manages: N ...`) computed from that same single-level scan, never a graph. "Flat" means exactly this one-hop semantic: links may compose (B can itself manage C, and the board may indent that nesting read-only), but no edge ever adds inspection, control, or authority at another edge.

**Kernel rule 9 (five separate facts; a reply/direction is untrusted, not authority).** A `ManagerDirection` is durable input, structurally incapable of granting authority: it is plain text on the target's own doc, read only from the target's own projection (§6, labeled explicitly as *not a human, never a human intervention, never grants new authority*), and the target's own pass — under its own constraints — decides what to do about it. `direct_workstream` cannot create assignments, adopt/reject, or touch the target's execution safety/constraints/approvals; the same authority firewall that keeps a reply from completing work keeps a direction from commanding one. `ManagerNotice` is the mirror fact flowing the other way: an idempotent, `dedupKey`-deduplicated report (`finished:<passId>` / `attention:<attentionId>`) delivered by `deliverManagerNotices`, which the engine calls unconditionally every tick cycle — once more immediately before a cycle exits on a non-active status, because a conclude inside the tick's own pass happens after that cycle's delivery step; and once at tick entry when the stream is already `done`, so `weaver tick` on a concluded child repairs a stranded notice even though it refuses to run passes — and which re-derives candidates from durable facts (`conclusion`, open blocker attention) rather than consuming a queue — so a crash between conclude and delivery is repaired by any later tick, the same shape as `recoverCrashedAttempts`. Neither write path touches `spend.humanInterventions`, which remains incremented only by `src/humanActs.ts` and the two `cli.ts` call sites — asserted directly in tests, not just by code inspection.

## Deliberate MVP simplifications

A production platform would own these properly; Weaver simplifies without faking the invariant:

- **One JSON doc per workstream, whole-doc compare-and-swap** instead of per-domain services with their own stores. The revision contract is identical in shape; the granularity is not.
- **The lease is trusted locally** (single machine, expiry only) — no fencing tokens.
- **The provider is a directory** (`world/outbox`). Its job is to be a source of truth that *isn't* Weaver's state, so readback is a real read of a foreign record.
- **Workers run sequentially** in the tick, and worker completion wakes are immediate — parallelism is an engine concern the MVP doesn't need to prove continuity.
- **Evaluators are the coordinator itself** (`evaluate_reply` / `evaluate_observation`) rather than declared evaluator runs.

## Surprises worth knowing

- **Agent SDK `mcpServers` are serialized into the child process's `--mcp-config` argument.** Passing literal HTTP/SSE Authorization headers therefore exposes them to same-user process listings. Hoist static header values into generated environment variables before calling `query()`; Claude Code officially expands `$VAR` / `${VAR}` in MCP headers. Diagnostics must match process names only and never print arguments.
- **Remote MCP parity is a credential boundary, not a config copy.** OpenHands receives only one disposable relay URL/bearer per upstream server. The host resolves environment placeholders, starts stdio processes or authenticated HTTP/SSE clients, freezes the complete tool catalog, and forwards read/write calls while scrubbing durable values. Claude Code stores OAuth tokens privately and also loads project, managed, plugin, and Claude.ai connector scopes that `~/.claude.json` alone cannot reproduce; those variants must fail or keep automatic routing closed, never be silently omitted and called parity.
- **`docker run --rm` does not remove a still-running container when its host client is killed.** Every new OpenHands container is labeled with its Weaver owner host and pid; before another container starts, the adapter lists only that exact executor+host label and force-removes entries whose local owner no longer exists. Live/unknown owners fail safe and are never touched. Normal `finally` cleanup still stops the exact random container name first.
- **The Agent SDK works with Claude Code subscription identity** — an interactive machine login needs no `ANTHROPIC_API_KEY`; a headless host uses the long-lived `CLAUDE_CODE_OAUTH_TOKEN` produced by `claude setup-token`. Capacity rejection can arrive as an SDK error result instead of a thrown exception, so both result and exception paths must enter the same durable backoff. `SDKRateLimitInfo` may carry both plan and overage resets; the earliest future reset is the next legitimate retry, not the later timestamp. Registered headless identity is injected from Weaver's executor-only store into a fresh config boundary, never copied from a device credential file.
- **Codex MCP `auto` approval can still route mutating tools to a reviewer.** A headless thread under `approvalPolicy: 'never'` then cancels Weaver's own `submit_result`/coordinator mutations as “user cancelled MCP tool call.” `default_tools_approval_mode: 'approve'` is the deterministic owner approval and is safe only because it is scoped to the per-run `weaver` server, whose enabled-tool list is explicit and whose random bearer token is scrubbed before any handler sees model-authored arguments. Coordinator isolation also requires a fresh temporary `CODEX_HOME`; read-only sandboxing alone would still admit user rules, MCP servers, and session history. Codex otherwise injects its working directory as environment context: because the coordinator cwd is disposable, that context is disabled and the bridge independently refuses any mutation argument containing the temporary path, so a model can never turn process plumbing into a durable assignment workspace.
- **Codex `workspace-write` is not the boundary for a declared host-process worker.** The official sandbox protects `.git` pointer files, resolved worktree gitdirs, and their contents recursively; its writable-root model can also block host daemons and caches outside the configured directories. Weaver therefore starts an ordinary `codex-sdk` worker with `danger-full-access`, matching the local Claude worker's ordinary coding-agent surface and the executor's `host-process` isolation declaration. That changes capability, not authority: reversible `work` is governed by its bounded assignment, irreversible egress still requires the `action` lifecycle and live Pilot supervision, and Codex actions fail closed until the SDK supplies that callback. The coordinator remains a separate hermetic, read-only process.
- **A credential-bearing host turns an executor label into a real isolation decision.** Pi's temporary `HOME` and Codex's fresh thread do not stop a same-UID host process reading absolute credential paths; copying a laptop's device login onto the box is worse. The GCP helper therefore refuses every ordinary-worker route and fallback except the existing OpenHands container seam, refuses Codex and Claude device state entirely, and runs its restricted coordinator through the Claude Agent SDK with a `CLAUDE_CODE_OAUTH_TOKEN` created by `claude setup-token`. That subscription route uses a fresh empty `CLAUDE_CONFIG_DIR`, strips ambient Claude/OpenRouter identity, refuses `ANTHROPIC_API_KEY`, and has an explicitly empty fallback chain; OpenRouter is confined to the isolated OpenHands worker route. `push-env` forces this hosted profile and filters provider keys out of `/etc/weaver/env`; identities exist only in the exact-synchronized executor store. Global worker credentials stay separate: `push-worker-secrets NAME...` renders only named records from the local global store, sends values solely on SSH stdin, and exactly replaces the host's mode-`0600` global store so omission is revocation. It provisions rootless Docker rather than adding `weaver` to the root-equivalent Docker group. Rootless Docker's `host-gateway` resolves to its inner bridge rather than the host: the hosted provisioner records the VM's private IPv4, the executor maps only `host.docker.internal` to it, and preflight proves the value is a local interface instead of widening the container to host networking. The GCP profile sets `WEAVER_DETERMINISTIC_ACTIONS_ONLY=1`: a model-driven action sharing the controller UID could read controller credentials even if no token were injected, so only an exact `exec.run` command may enter the hosted action lane. Preflight proves the setup-token identity exists, API/device identity is absent, the separate Pilot unit user owns the exact loopback listener, invalid/correct Pilot bearer responses, and success from the installed shared clients before systemd may start. Systemd normally applies the unit's `User=` to `ExecStartPre` too; the root-owned gate uses the `+` prefix so Linux exposes the other service's PID metadata, while `ExecStart` remains unprivileged. Either failure blocks the runner.
- **A hosted action lane cannot borrow the operator's ambient GitHub identity.** A personal `gh` device login or PAT on the runner survives beyond one assignment, crosses repository boundaries, and makes the human the remote principal. Hosted repository access therefore uses a dedicated GitHub App installed across the intended repository estate: all organization repositories for an organization-wide fleet, or a selected subset when its charter is narrower. Installation defines the fleet ceiling, but never an individual run's grant. The private key remains in the controller's executor-only secret store; a read-only token is minted for preflight, literal `gh`/Git remote reads, deconfliction, conflict watching, and verification, while a write-capable token is minted only after durable approval and immediately before an exact repo-egress command. `gh` consumes `GH_TOKEN`; Git receives the same repo-scoped token through process-local `GIT_CONFIG_*` entries whose exact-`github.com` credential helper references the variable, clears inherited helpers, disables prompting, and persists nothing. Both token lifecycles request explicit permission maps and are narrowed to the repository resolved from the assignment checkout; the mint response must confirm that exact owner/repository. A typed operator-repairable cwd/credential/installation-scope failure before claim settles the action with zero attempts and one coordinator wake, never a hot-loop or human card; transient provider and programming failures cannot enter that durable path. Ordinary worker containers receive neither key nor token — no work path mints one, and both container executors forward an allowlisted environment — and hosted same-UID model actions are structurally disabled. The engine-run command that does receive a token gets it from a scrubbed environment (below), with at least fifteen minutes of token lifetime left, and only the token itself joins the redaction set. Hosted preflight rejects personal `gh` state, Git credential files, static `GH_TOKEN`/`GITHUB_TOKEN` values, missing App credentials, or an App that cannot authenticate. This is identity isolation, not an alternative authority path: Pilot and the action lifecycle remain mandatory for repository egress.
- **A worker directory is a mount, so naming one is an authority decision.** Until 2026-09-21 `read_dirs` and the work cwd were checked only for being absolute. On 2026-09-14 a repair workstream on the hosted fleet (`repair-github-app-action-prep-origin`, `asg_b997afe1`, adopted) was dispatched with `/home/weaver/state` and `/home/weaver/.weaver` as read dirs; OpenHands bind-mounts every declared directory read-write, and `/home/weaver/state/executor-secrets.env` holds the GitHub App private key, the Pilot bearer, and the model credentials. "Ordinary containers get neither the App key nor a token" was true of the environment and false of the filesystem. `workerDirectoryRefusal` ([`src/executor/workspaceMounts.ts`](../src/executor/workspaceMounts.ts)) now refuses any directory that is, contains, or sits under `WEAVER_HOME`, the executor-secret store's directory, `/etc/weaver`, the running Weaver installation itself (a worker that can write the runner's source runs as the runner at its next restart; the same repair workstream mounted `/opt/weaver` read-write in four assignments), the runner user's `~/.ssh`, `~/.config`, `~/.weaver`, `~/.claude`, `~/.codex` (and `CLAUDE_CONFIG_DIR`/`CODEX_HOME` where set), the Docker socket, or `/proc`, and refuses `/` and the home directory themselves. Symlinks — including a dangling one and a symlinked ancestor of a path that does not exist yet — are resolved before comparing. The one carve-out is the neutral workspace root (`WEAVER_WORKSPACE_ROOT`), because the Docker/Railway layout deliberately puts it inside `WEAVER_HOME`; a directory under it is still refused if it *contains* a protected path. The check runs at three sites: `create_assignment` (and `weaver assign-action` without `--run`) refuses with guidance to name a checkout, worktree, or clone instead; `runWorker` re-checks on the execution host — whose `WEAVER_HOME` may differ from the coordinator's, and whose queue may hold assignments recorded before the check — and fails the assignment with zero Attempts and one coordinator wake; and both container planners (`planWorkspaceMounts`, `planContainerRun`) check the exact paths they hand Docker. An engine-run `exec_run` action's cwd is exempt: no model process and no mount ever receives it. On an operator Mac the checkout that holds the default `./state` is itself refused as a worker directory, so work on that repository names a worktree or clone.
- **An engine-run command is not the runner, so it does not inherit the runner's environment.** `runActionCommand` was spawned with `{...process.env, ...secrets}`. On the hosted runner `process.env` carries `WEAVER_STORE` — the Postgres URL with write credentials to the shared store — so a Pilot-approved but model-authored `exec_run` or `exec_verify` could have written to the store directly, around the revision-checked `mutate()` path. `engineCommandEnv` ([`src/secrets.ts`](../src/secrets.ts)) now builds every engine command environment — preflight, readback, and execution of an approved action, plus the harness's own `git`/`gh` probes in a model-influenced checkout (deconfliction, PR-conflict watching, origin resolution) — from `process.env` minus `WEAVER_STORE`, `WEAVER_GITHUB_APP_*`, every executor-store name, and the model/provider credential and login-selector families (`ANTHROPIC_*`, `OPENAI_*`, `OPENROUTER_*`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CONFIG_DIR`, `CODEX_*`, `ZAI_*`/`Z_AI_*`/`ZHIPU_*`, `WEAVER_MODEL_API_KEY`, `LLM_API_KEY`, `PRIME_API_KEY`, the serve and Pilot bearers), then adds the action's applicable worker secrets and the App environment minted for it. `PATH`, `HOME`, and ordinary Git/`gh` configuration survive, so `git push` still authenticates through the App's process-local credential helper. A selected value cannot reintroduce the store URL, the App identity, or an executor-registered name.
- **A redaction set is for secrets, not for everything that rode in with one.** The App environment's Git plumbing includes `GIT_CONFIG_VALUE_3=true`; putting the whole environment into the action's redaction set rewrote every literal `true` in action output as `«secret:GIT_CONFIG_VALUE_3»` — 227 markers in the fleet by 2026-09-21, and one workstream had to `sed` them out of a PR body before posting it. `githubApp.ts` now names its plumbing (`GITHUB_APP_GIT_PLUMBING_ENV`) and `githubAppRedactionSecrets` contributes only `GH_TOKEN`. The installation token also has a lifetime floor for actions: the mint normally reuses a cached token until five minutes before expiry, so preflight, execution, and readback pass `minRemainingMs` of fifteen minutes (longer if the bounded command and verifier retries ever outgrow it) and receive a fresh token otherwise.
- **Pi's exported `rpc-entry` already selects RPC mode.** Adding a second `--mode rpc` changes the CLI contract, so the pinned package entry is the executable and Weaver supplies only the fresh `--no-session` run flags. The run-bound extension must register the disposable provider before model resolution and delete its provider, MCP, and submission environment records before Pi's Bash tool starts. Likewise, Weaver's local provider-proxy turn ceiling returns HTTP 409: returning 429 would make the shared classifier persist a false provider-capacity backoff for a harness-owned structural limit.
- `settingSources` now follows CLI defaults when omitted. Workers request `user`/`project`/`local` settings because they are regular Code sessions; coordinator and helper model calls explicitly pass `[]` plus `strictMcpConfig: true`. That hermeticity is load-bearing: the projection or typed helper input must be the model's whole position.
- Yarn 4 + the `typescript` package: bare `yarn add -D typescript` resolved to the TS 7 native preview, which broke Yarn's patch protocol. Pinned to `^5.9.0`.
- **A heartbeat proves the poll loop runs, not that the host can commit.** `mutate()` writes its printout receipt under `WEAVER_HOME` before COMMIT on every backend, so when the hosted VM's 30 GB disk filled on 2026-09-10 every tick died on `ENOSPC` inside the first arrival (crash recovery, `wakes.fired`) with nothing written, four ticks per five seconds, for four days — while `runner_presence` (a pure database write) stayed seconds fresh and every dashboard read the fleet as healthy. The three passes whose SDK subprocesses were mid-flight stayed `running` with expired leases because the recovery that would have marked them is itself a write. The disk was filled by worker leftovers (`/tmp` clones, a Yarn v1 cache from provisioning, worktrees) rather than Weaver state (153 MB). The loop now probes the state directory each poll (`runnerHomeHealth`: the heartbeat-file write plus a free-space floor) and, while it fails, publishes `RunnerPresence.degraded` with no seats and dispatches nothing; `operatorCapacityPresentation` renders the reason. The receipt-before-COMMIT order is deliberately unchanged: a committed head must always have its transition, and the probe is what keeps that contract from freezing the fleet.
- **Work labels were never a runtime security class.** `research`, `work_product`, `communication_draft`, and `evidence` were once assignment "kinds", but every branch in the code keys off `=== 'action'` — nothing ever read the other four — so they were removed: a worker now has exactly two lifecycles, `work` and `action`. All `work` assignments share the ordinary Code prompt and tool preset, with the operator's configured MCP servers used read AND write; keeping a tracker in sync (an issue's status, a comment, a label) is ordinary work, not a gated effect. The line that matters is drawn by *consequence* — an `action` is one irreversible egress to the outside world (a message to a person, a spend, a merge/deploy/push), gated and readback-verified — never by which tool is used or by whether a write happens to be remote. (Enforcement caveat: a `work` worker still runs with permissions bypassed, so today that boundary is held by the brief and the prompt, not by the substrate; structurally containing every worker's egress at the executor seam is the standing follow-up.)
- **A readback against a JSON API must not grep a URL.** Slack's `conversations.history` escapes forward slashes, so a posted `https://engineering.example.com/2026-08-06` comes back as `engineering.example.com\/2026-08-06` and a verify command grepping the URL form matches nothing — forever. The failure mode is the worst shape available: a readback that *can only fail* blocks adoption of an action whose effect actually landed, and re-running it is exactly the duplicate send the invariant exists to prevent. Grep the bare stable token instead, and check any new readback against a real API response before trusting it.
- **`WEAVER_WORKER_MODEL` names a model for the worker's *executor*, not for every model call in the harness.** When the fleet moved workers to the Pi executor (`WEAVER_WORKER_MODEL=zai-coding-plan/glm-5.3`), the intake derivation and `weaver ask` — which always run through the machine's local Claude SDK login — kept reusing `workerModel()` and started handing the Claude SDK a z.ai model id. The same failure later recurred with the unprefixed Codex model `gpt-5.6-sol`, proving that slash detection is not an executor boundary. Every such pass failed; intake's catch-all shipped its deterministic fallback, so `weaver do` produced word-mash slugs before anyone connected the two. Three rules came out of it: `WEAVER_ASK_MODEL` is the explicit seat, otherwise local-SDK text passes reuse the worker model only when its executor is `local-sdk` and it names the Claude family, and a derivation fallback is *reported* on stderr — a degraded mode the operator cannot see is indistinguishable from a naming bug.
- **A capacity wait is cleared by evidence, not by time — so a wait can outlive the execution target that caused it.** `clearCapacityBackoff` runs only when the same executor/provider/model succeeds (`coordinator.ts`, `worker.ts`) or when the local Claude credential-change probe confirms that exact Claude target (`runner.ts`). Change a configured model after a backoff and the old entry can remain as history. Requiring proof is the right call — Weaver must not assume a provider recovered because a clock passed — but `capacity.byModel` is the historical field name for last-observed target records, not a claim about the present. The shared presentation projection therefore considers configured roles, fallback availability, intended queued work, and retry time before it can say `WAITING`; full inspection retains orphaned records.
- **A live pid is not a live runner, and a live runner is not a seated one.** (2026-09-02/03) A Mac runner spent 24 hours failing every poll with `getaddrinfo ENOTFOUND` for the fleet Postgres after a network change — fresh processes on the same Mac resolved the host fine — and nothing restarted it because launchd only watches the pid; `runLoop` now exits after five minutes of unbroken failures so the supervisor relaunches it. The standby VM took the coordinator seat as designed, but its chain was Fable (weekly allowance exhausted) then OpenRouter (out of credits), so every pass on the fleet also failed for a day: coordinator-runner order decides who *may* claim, and says nothing about whether that host can *serve*. The hosted chain now carries `claude-opus-5` between them, and every seat in a chain must be a separate capacity pool.
- **`ALTER TABLE … IF NOT EXISTS` still takes the lock.** (2026-09-03) The Postgres store ran its schema DDL on every process start. `ADD COLUMN IF NOT EXISTS` and `SET DEFAULT` queue for an ACCESS EXCLUSIVE lock *before* discovering there is nothing to do, and a queued exclusive lock blocks every later reader and writer on the table. One orphaned backend — a client that died mid-transaction with no FIN, holding a row lock — turned every new CLI/runner process's schema pass into a fleet-wide wedge for three hours while both runners looked "live". The store now checks the catalog first (no table locks) and runs DDL only when a piece is genuinely missing, and every pooled session carries `connectionTimeoutMillis`, `statement_timeout`, `lock_timeout`, and `idle_in_transaction_session_timeout` (constants in `src/store/pg.ts`) so a hang becomes a failure the runner's outage exit can count and an orphaned transaction is ended by the server.
- **An unhandled `'error'` on a checked-out pg client ends the process.** node-postgres reports a connection that dies between queries as an `'error'` event — on the pool for an idle client, on the `Client` itself for a checked-out one. The resident runner died to `read EHOSTUNREACH` this way, and its supervisor's restart orphaned every in-flight run. The pool's `'connect'` hook now attaches a listener to every client; the in-flight query still rejects through its caller. That fix missed the one `pg.Client` built outside the pool — the dedicated tick-lock session in `tryTickLock` — and the hosted runner died again on 2026-09-14 (`Connection terminated unexpectedly`, exit 1) with two passes mid-flight, which then sat behind expired leases until their next tick. Every `new pg.Client` needs the listener, not just the pool's; the lock session's listener also records that the server has released the advisory lock with the session, so the tick finishes under the revision check alone and its release does not ask a dead session to unlock (a completed tick would otherwise throw at its last step and be re-dispatched as failed). `store.test.ts` terminates the lock backend from another session to hold this.
- **A merged runner fix is not deployed until something on the host pulls it — and until 2026-09-15 nothing did.** The hosted VM's checkout only moved when a person with a live gcloud session ran `weaver-gcp update --restart`, so the degraded-disk probe and the tick-lock listener each sat merged and undeployed behind an expired cloud login, and every fleet incident ended with the same manual step. The runner already exits when its source moves (`runnerSourceStale`) and systemd relaunches it; the missing half was the pull. `bin/weaver-gcp-update.sh` runs from `weaver-update.timer` every five minutes as a root-owned copy (never out of the service-user-owned checkout, same rule as the launch preflight), fast-forwards to `origin/main`, reinstalls immutably, restarts only `weaver-serve`, and refuses to move a checkout that cannot fast-forward. Weaver merges its own PRs; this is what makes a merge reach the fleet without anyone at a laptop.
- **A launch gate that greps a state file for a word will one day refuse the launch on that word.** The hosted preflight decided "hosted GitHub MCP credentials" by `grep -Eqi 'github'` over the whole of `~/.claude.json`, Claude Code's 40 KB state file. On 2026-09-14 the coordinator's SDK cached a feature-flag name, `tengu_kairos_github_webhooks: false`, into it; the first restart after that — the self-updater's very first roll-forward, 2026-09-15 10:14 UTC — was refused, `weaver-run` sat in `activating` looping through `Restart=always`, and the fleet was down for 9 minutes until the gate was fixed to read what the files DECLARE: `mcpServers`/`servers` entries at any depth, parsed with node, refused on a GitHub-named server or a declaration carrying a token or endpoint, failing closed on a file that is not JSON. Every other check in that preflight that reads a file by substring is the same bug waiting; and an auto-updater makes the launch gate run far more often than a hand restart did, so a false refusal now costs the fleet rather than an operator's afternoon.
- **A confinement boundary is a decision about WHERE a process runs, not WHICH model it talks to — and the hosted worker lane had conflated the two.** The credential-bearing host refuses host-process workers because a process sharing the `weaver` UID can read the executor secret store, and the only containerized route was OpenHands, whose model is whatever the OpenRouter seat offers. So "workers must be confined" silently became "workers must be OpenRouter", the Claude subscription the founder pays for was reachable only by the coordinator, and when the single OpenRouter account ran dry on 2026-09-14 all 194 worker attempts in a day parked on `usage_limit` while Opus sat idle. `src/executor/claudeContainer.ts` separates the two: the SDK's `spawnClaudeCodeProcess` hook starts Claude Code as `docker run` in the same rootless worker image, mounting only the SDK binary (ro), the workspace and declared read dirs at their host paths, forwarding an allowlisted environment by NAME (identity, declared secrets, SDK protocol variables — never `WEAVER_STORE`, the Docker socket or the App key), as uid 0 which under rootless Docker is the runner itself (so files come out runner-owned; `IS_SANDBOX=1` lets Claude accept `bypassPermissions` as that root). The hosted profile is now Claude-first for workers with OpenHands/OpenRouter behind it. Two things the rollout must get right: the preflight refuses the profile on a checkout whose code predates the spawner (an old runner would honour `WEAVER_EXECUTOR=local-sdk` as a HOST process), and a declared action is never containerized (Pilot supervises it live where the engine can read the effect back). And one thing the first live cutover got wrong: the worker image has an entrypoint of its own (the OpenHands agent server), which took the Claude binary path as ITS arguments — the preflight proof refused with "the image cannot run the SDK's Claude Code binary", the runner sat in `activating` until the old profile was merged back, and the fix was `--entrypoint` in both the spawner and the proof. A gate that runs a command inside somebody else's image must say what the entrypoint is.
- **`weaver-install-env merge` replaces the WHOLE managed set, so a hand-rendered partial profile is a revocation of every managed key it omits — including `WEAVER_SERVE_TOKEN`.** Restoring the hosted profile by hand on 2026-09-15 (the operator laptop had no executor secrets registered, so a real `push-env` would have emptied the host's credential store), I filtered `WEAVER_SERVE_TOKEN` out of the render to avoid overwriting it; the installer read the omission as "revoke" and `weaver-serve` crash-looped for the next quarter hour on "WEAVER_SERVE_TOKEN must be set" while the runner beside it read healthy. Omission-is-revocation is the right rule for seats and credentials; the mistake was merging a render that was not complete. If a merge must be done on the host, do the whole thing there: read the current managed values from the host's own files into the render on the host, never trim the render on the laptop. `WEAVER_LOCAL_SDK_CONTAINER` and its image are in the managed set for the same reason — a profile that goes back to OpenHands must take the container flag with it.
- **A worker container is bounded in memory and runs as container root, because rootless Docker makes both host problems.** On 2026-09-18 three unbounded worker containers started within two minutes on the 8 GB, swapless hosted VM; RAM went from 3.5 GB to full in ten minutes, nothing was OOM-killed, the page cache thrashed (disk reads up a hundredfold), the frozen box missed its DHCP renewal, and the fleet was offline for 3.4 days. Both container executors now pass `--memory` and an equal `--memory-swap` from one helper ([`src/executor/containerLimits.ts`](../src/executor/containerLimits.ts); `WEAVER_WORKER_MEMORY_LIMIT`, default `4g`, `0`/`none`/`off` to opt out, anything malformed refuses the run), so a runaway is killed inside its own cgroup and the attempt fails like any other. The ceiling bounds one container, not the sum of concurrent seats. Rootless Docker enforces it only when the cgroup v2 memory controller is delegated to the Docker user; otherwise `docker run` warns, drops the limit, and still starts the worker (check `docker info` for `No memory limit support`). Separately, the OpenHands image runs as its own `openhands` user (uid 10001), which rootless Docker maps to subordinate host uid 175536: everything that worker wrote into the bind-mounted workspace came out owned by a uid the runner cannot modify, the fleet's checkout collected 367 such `.git` entries, and git refused the repo. OpenHands now runs with `--user 0` like the Claude container, since container root is the runner's own host uid; the 1.41.0 image needs nothing from the `openhands` user (HOME falls back to `/root`, and a real conversation's terminal and git commits work as root). Both changes move the OpenHands harness epoch to `openhands-agent-server-1.41.0-weaver.6`, keeping eval evidence from the unbounded non-root container separate.
- **A Pilot with no rules file is not a stopped Pilot — it is a Pilot running somebody else's policy.** Pilot resolves its config as `PILOT_CONFIG`, else `$PILOT_HOME/pilot.toml`, else `~/.pilot/pilot.toml`, and when that file cannot be read it logs one warning and judges every request with its compiled-in default rules. The hosted `weaver-pilot.service` was installed with no file, so the fleet's approval policy quietly diverged from the operator's: the self-merge carve-out that lives in the operator's Pilot rules (a learned fleet policy can never grant authority — kernel rule 11) did not exist on the host, and nothing on any dashboard said so. `bin/weaver-gcp.sh push-pilot-config <file>` now replaces that file exactly — contents only on SSH stdin, owned by `weaver-pilot`, mode `0600`, no restart because Pilot re-reads a changed file — and the launch preflight refuses an action-capable runner whose Pilot has no rules file, naming that command. The installer and the preflight resolve the path with byte-identical code from the unit's `Environment=`; a test installs through one and launches through the other. What the preflight cannot see: a Pilot able to write its home bootstraps a default file on first start, so "a file exists" is necessary, and `push-pilot-config` is what makes it the operator's. The same change fixed the launch commands' chaining: `start`/`restart` ran `preflight; systemctl …`, so a refused gate still restarted `weaver-run`, stopping a live runner that its own `ExecStartPre` then refused to start again — the chain is `&&` now.
